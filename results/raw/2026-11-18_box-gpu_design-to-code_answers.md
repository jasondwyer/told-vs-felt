## 1. Q1 — why (a)

**1.1 What a box is to n.** n's units run on OLMo-2-32B Instruct, a model p never touched; its questions compare n's arms with one another and with BK's published figures, never with p's runs. The one tie between n and p's box was convenience: G-ACQ's "shared with A-m1's units if the same box" (n §3), now moot. The program's rules on boxes are about splicing and characterization — a campaign never spliced across backends; every box characterized before an experimental forward — and n has run nothing on a GPU. A new class for n breaks nothing of record.

**1.2 Which class.** CLAUDE.md :91 describes the box as "A100/H100-class"; the H100 SXM is inside the words, at the memory p's 32B campaigns ran in (80 GB), and OLMo-2-32B in bf16 (about 64 GB, n §2.7) with a 1.3k-token context fits it as p's model fit the A100; the capture band is written to disk per read and holds no GPU memory worth the name. The H200's 141 GB buys headroom n has not been shown to need, at a price and a departure from :91's words (a dated note, not an edit: CLAUDE.md is never silently changed). So the H100 first; the H200 when the H100 has no stock at the word, the note recording it.

**1.3 Why not wait.** D_n is 2026-12-15 (n §7.4): LOCK-n v1.0 committed by then or N-pod is NOT-RUN. Between a working box and that lock stand the BACKEND extension and §2's label check, G-VEC, G-CAL-n (the seat reads every turn), G-ANL-n's canonical run, LOCK-n v0.1 (the seat's read), G-TIME-n and the PI's cap, G-VER, and the v1.0 draft (the seat's read) — five box sessions and three seat reads, each a day or two, with no STOP cycle. The A100's host refused its start at every attempt on 2026-11-17, and its GPU failed CUDA initialization twice the day before; the stock that moved in fifteen reads on 2026-11-15 is a reason the A100 may return, not a date. ## 3. Q3 — the restarted A100, by the protocol's own test

**3.1 (a), with the test as the condition.** The backend identifier is the record's definition of a backend (m:267: a box of one class gives one identifier; `resume.py` :146), and it cannot see the driver by design. The protocol already has the test for a box that claims to be the one characterized: respawn (ii) "the new artifact byte-identical to the committed one" (A, B, C exact). So: if the A100 pod starts healthy and (ii) re-runs with its artifact byte-identical to `7ab4d2f`'s and its identifier `641ee466f4553b6a`, the backend of record stands for n as the seat's answers of 2026-11-15 §5.4 had it, and the driver change (595.91.07 → 595.112.07) is recorded in that respawn's dated entry and as a dated note on `7ab4d2f`'s. n's step 4 then runs as drafted, its driver committed first.

**3.2 Why not (b).** The laptop's OS build is in the backend because MLX's kernels ship with the OS, so a build change can change the numerics without any other sign; on the pod the kernels are torch's, whose build is in the provenance (`olmo_hf.py` :326), and the driver's effect on the numerics, if any, is exactly what (ii)'s byte-identity measures. A driver change that leaves A, B and C byte-identical has changed nothing the record defines as the backend. One that does not is a new backend by the protocol's own result: a new `BACKEND — characterization` entry, and §2's items 4–7 for the A100 as for a Hopper box.

**3.3 The order on a healthy start.** The probe; (i); (ii) with the byte-identity read; then, under 3.1, n's step-4 smoke (never of record) and the driver's commit; under 3.2, §2 from item 3. If a Hopper pod has been created by then, the A100 is not used for n and is stopped; one box.
